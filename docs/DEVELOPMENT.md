## Preview 模型配置继承 · 2026-10-18

固定 Wrangler 4.135.0 的 `preview` 上传不使用普通部署的 `keep_vars`。保留 `--ignore-base-config` 和显式测试 D1/R2；需要真实模型的分支，在该 Preview 的运行时先安全设置 `MODEL_API_KEY`（Secret）、`MODEL_BASE_URL`、`MODEL_NAME`，再仅为该分支的**构建变量**设置 `AI_MLS_PREVIEW_MODEL_INHERIT=1`。脚本仅生成这三个名字的 `previews.unsafe.bindings` / `type: inherit`，从目标 Preview 的现有部署继承，不读取密钥，也不继承父 Worker 的全量绑定。其他分支默认不启用，继续支持无模型的人工草稿验收；此开关不能代替首次配置凭据。生产段配置不变。

采用 API 的显式继承类型是固定版本的窄范围兼容路径，升级 Wrangler 时必须复验。参考 [Preview 配置规则](https://developers.cloudflare.com/workers/previews/configuration/)；不能用一般 deploy 的 Secrets 或 keep_vars 说明代替 Preview 实测。验收必须在重新构建后核对三个 MODEL 绑定类型、两项公开参数、测试 D1/R2 与 Access，并用已有合成草稿最小验证模型可调用；不得仅根据构建成功判定通过。

回退时先停止该 Preview 自动构建，再回退脚本及分支开关；在恢复三个运行时参数并核对隔离前不重新部署。直接关闭开关后重建会再次移除模型绑定。生产不需要回滚。本地配置回归 10/10，用户重新录入测试 Secret 后连续两次原生重建均保留三个 MODEL 绑定，测试端点标记及提供方 HTTP 200/code 0 验证通过；空白图被 schema 拒绝，不计作识别质量成功。证据及边界见[模型评测报告](MODEL_EVALUATION.md#preview-配置继承修复与重建验收)；最终文档 head 的检查与绑定复核记在 PR #3。

### 合并门禁与串行验收

1. 每个 PR 必须通过 API 回归、类型检查、构建，以及使用模拟模型的关键浏览器闭环。检查必须对应拟合并的最新提交；改动后重新执行受影响验收。
2. 涉及模型、认证或存储的改动，在 Preview 使用测试账号和合成数据执行对应真实集成验收，保存结果供用户批准合并；不使用生产学生记录。
3. 共享测试资源同一时间只验收一个 PR。运行前记录 PR/SHA 和资源状态，验收期间其他分支不改写该资源；结束后清理本任务数据并释放占用。需要并行或 schema 不兼容时才增加临时资源。
4. 先证明 PR 分支可得到检查反馈，再配置 main 的必需检查和批准规则。main 上现有成功部署 Check 不能直接充当已验收的 PR 门禁。
5. 用户批准合并后由现有 Builds 发布；不把危险迁移混入 deploy 命令。发布证据记录 SHA、构建 ID、Worker 版本、检查结果和发布前良好版本。

## Risk & Rollback

### 恢复目标与备份

- 故障范围包括错误发布、错误配置、数据库误操作和图片误删；账户失去访问权及平台整体故障不在本轮恢复承诺内。
- RPO：最多损失 24 小时数据，以最近可验证的配套恢复点衡量。每天备份和超龄告警本身不保证达到该目标，需按实测耗时留出调度与重试余量；失败时明确标记不达标。
- RTO：发现故障后 4 小时内恢复服务，包含等待用户或在线 Agent 响应、所需审批及实际恢复的时间；不暂停计时。分别记录发现、响应、请求审批、批准和恢复完成时间。
- 每天形成配套 D1/R2 备份，保留 7 天。备份必须有批次清单、D1 恢复点/导出与所需 R2 对象的对应关系和校验；只观察两个任务成功不足以宣称可以配套恢复。
- 并发上传/删除期间如何形成一致的配套恢复点，是 M3 必须通过原型验证的技术条件。尚未选定具体同步方法，不能以需要生产停写为默认假设；若确需维护窗口，提出影响再审批。
- 图片副本独立保存，业务删除不立即传播到副本；备份受访问限制并按 7 天到期清除。不能无限保留已删除的学生图片。
- D1 Time Travel 可复用，但须核对套餐恢复窗口；若不足以提供所需恢复点，补充受控导出。R2 Bucket Lock 仅按需要评估备份副本，不给业务桶全量加锁，避免破坏删除流程。
- 演练使用合成数据和隔离资源，验证恢复后数据库引用的图片存在、校验正确、所有权不变，且上传—确认—复习闭环可用。测试环境不导入生产学生数据。

### 检查、告警与有限代码回滚

- 自动化负责检查与告警；用户或在线 Agent 执行响应。本轮不建设常驻 Agent 或无人值守回滚系统。
- 邮件为唯一通知入口，GitHub 保存后续处理证据。优先复用经核实可用的原生通知；覆盖不足时先提出最小补充方案。实施前确认收件地址并验证测试邮件送达。
- 告警覆盖应用关键检查失败及成功配套备份超过 24 小时；恢复状态和重复告警处理在实施中验证。GitHub 处理记录不是另一条通知链。
- 有限代码回滚已获用户预先授权，但须同时满足：发布前基线通过，发布后关键应用检查连续两次失败，有证据明确指向新版本，旧版本兼容当前数据。
- 满足条件时，用户或在线 Agent 可恢复到发布前记录的良好 Worker 版本，保留理由、版本、操作及复核证据。执行前复查没有较新发布，防止回滚错误版本。
- 原因不明、外部服务故障或兼容性不明确时，告警并等待用户处理。生产数据恢复、Access 变更及迁移始终需要用户单独批准。
- 恢复旧 Worker 版本可能同时恢复其绑定、变量等版本配置。实施中须比较配置差异；若涉及 Access 变更或其他超出有限代码回滚的影响，则停止并单独审批。
- 发布后默认使用安全、无业务写入的生产检查；完整写入闭环在隔离 Preview 验证。若无写入无法判定故障，再提出受控生产测试方案，不直接写入学生数据。

### 其他保护

- Preview 部署前核对数据库 ID、桶名、身份参数及服务绑定目标；缺失测试配置即停止，不回退到生产资源。Version URL 不作为隔离测试环境。
- 配置归仓前保存脱敏旧设置及当前版本，先比较测试产物；恢复配置不会自动恢复代码或数据。
- 保留当前身份 ID 命名空间；若变更身份提供方，先核对 owner 映射。登录成功不等于原数据归属正确。
- 迁移优先向后兼容，独立审批；数据恢复考虑恢复点后写入及 D1/R2 配套关系。保留可审计的紧急发布权限，普通开发凭据不授予无约束生产发布能力。

未来核查若迫使新增平台、扩大生产写入、放宽门禁或调整恢复目标，应重新提出取舍；不自行改变已确认边界。
