# PR 验收与合并

## 自动检查

每个拟合并提交必须通过 Cloudflare 应用发布的 `Workers Builds: ai-mls`，包含配置校验、API 回归、类型检查、构建、手机与桌面 Chromium 的模拟模型闭环。main 必需检查固定 Cloudflare 应用来源并要求分支与 main 同步。缺失或失败时停止合并；新提交需重新通过。

本地准备：Node 24、固定 pnpm，执行 `pnpm install --frozen-lockfile && pnpm build`、`pnpm exec playwright install chromium`、`pnpm test:browser`。测试只运行本地 Worker，重建本地 DB/R2 配置和临时数据目录；身份及模型在测试入口模拟，不验证线上 JWT 或真实模型。失败截图/trace、JSON 结果在 `outputs/browser/`；云端构建日志保存结果，需长期保留的失败附件人工脱敏后附到 PR。

## 按改动选择真实集成

| 改动范围 | 在独立 Preview 执行的验收 |
| --- | --- |
| 测试、文档或合并规则 | 确认最新 Check 与 PR head 对应；确认生产状态不变。没有业务改动时说明不重复模型调用的理由 |
| 构建、发布工具或绑定 | 核对 Preview 最终 D1/R2 与生产不同，Access 拦截匿名请求；授权身份加载、合成记录/图片持久化；生产设置和版本前后相同 |
| 模型请求、提示词、响应契约 | 用合成图片调用真实提供方，校验识别、失败重试、人工确认；只在测试目标配置专用模型凭据，不复制生产密钥 |
| 身份、授权、数据访问 | 两个实际测试身份验证列表/修改/删除/图片隔离、匿名和伪造头被拒；Access 变更另行批准 |
| D1/R2/schema、复习写入 | 合成上传、确认、复习提交、刷新；核对事件与图片引用，验证幂等、迁移和旧版兼容；生产迁移另行批准 |

多范围改动取并集。缺少凭据或第二测试身份时明确阻塞相应验收，不能以本地模拟替代真实集成通过。验收记录必须绑定 head SHA；新提交重新判断影响范围。仅文档修正可说明为何保留先前集成证据，最新构建检查仍须通过。

## 串行占用

共享测试 D1/R2 同时只允许一个写入验收。开始前读取所有开放 PR 的验收记录，记录 PR、head SHA、执行者、起止时间、资源别名及已有合成记录；冲突时等待释放。每次只操作本任务创建的合成数据。结束时记录保留或清理的 fixture、释放时间；需要不可恢复删除时按当次授权执行。构建中的浏览器测试使用独立本地状态，不占用共享云端数据。

## 用户批准与管理通道

仓库当前仅有 hilt21 管理员，Agent 也使用相同身份创建 PR。GitHub 作者不能批准自己的 PR，因此本阶段采用用户确认的方式：技术门禁强制检查与 PR 流程，用户在会话中批准具体 PR/head 后才可合并；不把自动检查、模板勾选或 Agent 审查当作用户批准。

单一身份不能在 GitHub 技术层区分人和 Agent。管理员的规则管理权限仅作应急通道；若必须调整或绕过，先取得用户明确批准，在 PR 记录原规则、原因、批准、实际合并 SHA 和恢复结果。日常合并不绕过检查。以后引入独立提交身份/审查人时，才启用独立 approving review，不提前制造无法自审的死锁。

## 发布边界

当前生产仍使用原有构建/发布命令；本阶段只调整 Preview 检查和 GitHub 门禁。main 合并会触发现有生产自动发布，M3 恢复准备及 M4 授权完成前保持 PR 未合并。Sites 冻结继续等待资源映射。
